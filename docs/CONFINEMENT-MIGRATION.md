# Confining every poppy — migration plan

Scope: turn on `backend.isolation: "strict"` for every poppy. Under that setting the host spawns the backend with Node's permission model on: read = install dir + host data dir + OS temp; write = data dir + OS temp; child processes denied. Verified at `/Users/mt/Projects/agentspoppy/packages/broker/src/extensions/backend-host.ts:145-160` (`confinementOptions`: returns `null` unless `backend.isolation === "strict"`; `read = [spec.root, dataDir, tmp]`, `write = [dataDir, tmp]`; only `--permission` and `--allow-fs-*` flags are emitted, so `--allow-child-process` is never granted) and applied at `backend-host.ts:288-296` (the `NODE_OPTIONS` is set on the spawned child only).

Reference implementation: `/Users/mt/Projects/liveops-poppy/extension.json:157-162` — `"runtime": "node22"`, `"isolation": "strict"`.

**Evidence note.** Everything about the AgentsPoppy host, MailPoppy, TrafficPoppy, VM-Poppy and CrewPoppy cited below with a file:line I opened and read in this pass. Statements that come only from the supplied audit's *live runs* (booting a poppy's shipped bundle under the real flags) are labelled "audit-observed" — I did not re-run them.

## 1. Attachments: the answer

**Short answer: uploading is unaffected. Downloading works too, but MailPoppy's current default download route breaks — and it breaks loudly, not gracefully. That route has to be removed before MailPoppy can be confined. The replacement already exists in MailPoppy's own code.**

### Upload (file from the user's disk → an email)

Not affected by confinement at all, because the confined process is never involved.

- The file is picked and read **in the frontend**, which is a browser frame, not the backend process. `/Users/mt/Projects/mailpoppy/apps/desktop/src/lib/attachments.ts:6-25` — `fileToAttachment(file: File)` uses `FileReader.readAsDataURL` and returns base64. No `node:fs` anywhere in that path.
- Confinement is a `NODE_OPTIONS` string applied only to the spawned backend child (`backend-host.ts:288-296`). The frontend runs in an iframe (`/Users/mt/Projects/agentspoppy/app/src/extensions/ExtensionFrame.tsx:85`), which has no filesystem API to restrict.
- The base64 then goes either straight to the network (MailPoppy PUTs ≥1 MB attachments to a presigned S3 URL from the frontend) or into the backend as a JSON body through the host proxy: `POST /extensions/:id/backend` (`/Users/mt/Projects/agentspoppy/packages/broker/src/http.ts:411-420`) → `registry.proxyBackend` (`/Users/mt/Projects/agentspoppy/packages/broker/src/extensions/registry.ts:280-296`), which `JSON.stringify`s the body and fetches the backend's loopback port. Network is untouched by the permission model.

Four honest limits on upload, none of them caused by confinement:
1. **JSON only.** `proxyBackend` stringifies the body and reads the reply with `res.text()` (`registry.ts:286-295`). Binary must be base64 (~33% bigger). No streaming, no multipart.
2. **No size cap.** The broker buffers the whole request body in memory (audit-observed at `http.ts:22-24`). A huge upload is a memory cost, not a rejection.
3. If a confined backend wants the uploaded bytes **on disk**, it may only write them under the data dir or OS temp (`backend-host.ts:153-154`).
4. **UNVERIFIED:** that the OS file picker actually opens for `<input type="file">` inside the sandboxed iframe in the *packaged* Tauri webview. The sandbox attribute does not forbid it (`ExtensionFrame.tsx:85` — `allow-scripts allow-same-origin allow-forms allow-popups allow-downloads`), and MailPoppy ships such an input, but I found no test and no recorded in-container run. Ten-minute manual check; see step 0 of the plan.

### Download (attachment → a file the user keeps)

This is the direction that needs the host, and the host has a purpose-built route that survives confinement completely.

- `GET /ext-dl/:id/local-download/:token` — `/Users/mt/Projects/agentspoppy/packages/broker/src/http.ts:429-441`. It matches exactly four path segments with `parts[2] === "local-download"`, then calls `registry.fetchBackendBytes` (`registry.ts:306-319`), which is a plain `fetch("http://127.0.0.1:<port>" + path)` copying status, content-type and content-disposition back as raw bytes. **No filesystem call anywhere in that path.**
- The route is exempt from the broker's auth gate (`http.ts:123` — `isAssetRoute = parts[0] === "ext-ui" || parts[0] === "ext-dl"`), which is why the OS browser, carrying no bearer token, can fetch it.
- The backend mints the token itself; the broker neither generates nor validates it. The comment at `http.ts:427-428` asserts tokens are single-use and short-lived — that is a statement about poppies, not something the broker enforces.
- MailPoppy already implements exactly this: `POST /local-download` at `/Users/mt/Projects/mailpoppy/apps/desktop/node-sidecar/src/index.ts:146-165` mints a `randomUUID()` and stores the decoded Buffer in an **in-memory Map** with a 60 s TTL; `GET /local-download/:token` at `index.ts:167-181` deletes the entry (single-use) and replies with `content-disposition: attachment`. Nothing touches disk. The frontend builds the URL from its own `window.location` (`/Users/mt/Projects/mailpoppy/apps/desktop/src/lib/localDownload.ts:19-28`) and opens it with `openExternal`.

**So the download direction is covered — but not the way MailPoppy currently uses it by default.**

- The *preferred* path is `saveBytesToDownloads` → `POST /local-download/save` (`node-sidecar/src/index.ts:188-204`), which does `fsp.mkdir(join(homedir(), "Downloads"))`, an `existsSync` collision loop, and `fsp.writeFile`. Under strict isolation the write allowlist is data dir + temp only (`backend-host.ts:153-154`). This route dies. (Audit-observed live: it returned `ERR_ACCESS_DENIED`.)
- **And it fails without falling back.** `localDownload.ts:96` only falls back to the browser handoff when the error text matches `/sidecar 404/` — i.e. only when the route is *missing*. An access-denied surfaces as a 500, so the fallback never fires and the user sees an error instead of a download.
- There is no native save dialog to fall back on either: the Tauri capability file lists no dialog permission and no `tauri-plugin-dialog` is present (audit-observed). The browser handoff is the only file-out mechanism the host offers.

**What has to be built:** nothing new in the host, and nothing new in MailPoppy. The work is deletion: remove `POST /local-download/save` and make `downloadBytesViaSidecar` the only path. That is the fix, and it is small.

**One unresolved contradiction worth settling before other poppies copy a design.** CrewPoppy's code comment says a sandboxed frame cannot download at all (`/Users/mt/Projects/mission-control-poppy/backend/src/crew-csv.ts:106-109`, citing a founder observation on 2026-08-01), and that is the stated reason it writes to `~/Downloads` from the backend. But LiveOpsPoppy — the confined reference poppy — ships a plain blob download in its frontend (`/Users/mt/Projects/liveops-poppy/frontend/src/Sdk.tsx:56-63`: `createObjectURL` → `a.download = "LiveOps.cs"` → `a.click()`), and the host's iframe does carry `allow-downloads` (`ExtensionFrame.tsx:85`). Both cannot be right about the same host. **UNVERIFIED which.** Settle it by clicking LiveOpsPoppy's "Download LiveOps.cs" button in the installed app. If a file lands, a frontend blob is the cheapest file-out mechanism and needs no backend route at all. If it does not, the `/ext-dl` token handoff is the answer everywhere.

### Step 2 — MailPoppy: accept `dataDir` from the bootstrap (small)

Add `dataDir?: string` to the `BackendBootstrap` interface (`node-sidecar/src/agentspoppyBroker.ts:254-263`) and carry it through the returned object (`:278-284`), which currently drops it. Expose it to the rest of the sidecar.

**How you know it worked:** log the resolved data dir at boot in the container and see the host's `extension-data/com.mailpoppy.desktop` path.

### Step 3 — MailPoppy: move its own state into `dataDir` (small)

- Ledger: `ledger.ts:28` already reads `process.env.MAILPOPPY_LEDGER ?? join(homedir(), ".mailpoppy", ...)` — change the fallback to the data dir.
- Buyer id: same shape at `buyerId.ts:24`.

Two things to get right, both under-rated if you treat these as "just files":

- **The ledger is an input to teardown, not only a transparency display.** `readLedger` returns `[]` on any failure (`ledger.ts:32-40`) and `record` swallows write errors (`:43-56`), so losing it is silent. The audit traced it feeding `discoverProvisionedDomains` → `teardownAll`, which decides which SES identities and DNS records to delete at uninstall. An empty ledger can therefore leave live mail infrastructure behind in the user's AWS account. Do not ship confinement with a broken ledger.
- **Buyer id is a paid-customer link.** `readStored` is caught but `write()` is not (`buyerId.ts:42-45`) — under confinement the route 500s. Moving the file also means an existing `~/.mailpoppy/buyer-id.json` becomes unreadable and the user mints a new id. `getOrCreateBuyerId` accepts a `seed`, so plan a one-time carry-over or accept one re-link.

**How you know it worked:** run the poppy unconfined with the new paths; check the files appear under the host's data dir; open the AWS Resources tab and see ledger entries; hit the billing portal and get the same buyer id twice.

### Step 4 — MailPoppy: stop writing to `~/Downloads` (medium)

- Delete `POST /local-download/save` (`node-sidecar/src/index.ts:188-204`) and make `downloadBytesViaSidecar` (`localDownload.ts:50-64`) the only path in `saveBytesToDownloads` (`localDownload.ts:82-100`). At minimum the `/sidecar 404/` guard at `localDownload.ts:96` must go — otherwise the failure mode is an error message, not a download.
- Fix the mailbox-import template save (`mailboxImport.ts:186-201`). It loops over `[join(homedir(),"Downloads"), tmpdir()]` and calls `existsSync(dir)` first. Under the permission model `existsSync` on a denied path **throws** rather than returning false (audit-observed), so the loop dies on the first candidate and never reaches the temp fallback that would have worked. Cheapest fix: drop `~/Downloads` from the list. Better: hand the workbook bytes to the same one-shot token path as attachments.
- Update any user-facing text that says a file was saved to Downloads.

**How you know it worked:** download an email attachment in the container and get a file; download the bulk-mailbox template and get a file; `grep -rn "Downloads" node-sidecar/src` returns nothing.

### Step 5 — MailPoppy: retire the local AWS credential plane (small, but touches several files)

Under the container the local credential path is already mostly dead and confinement finishes it off. The host strips the entire `AWS_*` namespace before spawning — `poppyEnv` at `backend-host.ts:117-127`, which drops every key matching `/^AWS_/i` (and `NODE_OPTIONS`) — so `AWS_PROFILE`, `AWS_SHARED_CREDENTIALS_FILE` and `AWS_CONFIG_FILE` never reach the backend, confined or not.

What to change:

- `awsProfile.ts:17-28` (`mailpoppyProfileExists` — `existsSync` + `readFileSync` of `~/.aws/credentials`) and `:50-60` (`mkdirSync` `~/.aws` + `writeFileSync` the `[mailpoppy]` profile). Gate both off in container mode; ideally compile the wizard's credential-entry panel out too.
- **Two paths resolve credentials with `fromIni` and have no broker fallback at all**, unlike `provisioning.ts` which tries the broker first: `migration.ts:154` (`const credentials = ctx.profile ? fromIni(...) : undefined` feeding the S3 and DynamoDB clients used by the whole WorkMail/IMAP import) and `capabilities.ts:58` (same shape, feeding the wizard's permission lights). In the container these silently produce no credentials — the import feature is dead and the permissions panel reads "nothing connected" while readiness says ready. Give both the same `brokerCredentials() ?? fromIni(...)` precedence. This is already open as task #51; confinement turns it from a preference into a hard feature loss.
- The AWS SDK's own reads of `~/.aws/config` and `~/.aws/credentials` need **no** change: they are wrapped in a swallowing catch inside `@smithy`, so a denial degrades to an empty config (audit-observed, and the same mechanism is why LiveOpsPoppy already runs strict with the SDK). Worth recording as a watch item: that catch is vendored third-party code, not a contract.
- Also update the user guidance. `index.ts` advises re-authenticating with `aws sso login`; inside a confined container no local re-auth can ever be seen, because every home-directory credential source — named profile, SSO token cache, `login_session`, `credential_process` — is denied. Point the user at the AgentsPoppy connection instead.

**How you know it worked:** in the container, the wizard shows a connected, ready state with the permission lights lit; an IMAP import against a test server actually writes rows; nothing in the backend reads `~/.aws`.

## 4. The two defaults to flip at the end

### (a) `backend.isolation` defaults to `"strict"` instead of `"none"`

Today the default is unconfined: `confinementOptions` returns `null` unless the manifest says `"strict"` (`backend-host.ts:150`), and `SECURITY_MECHANISM.md:153` states the default is `"none"` for compatibility.

**What breaks when it flips:** every existing poppy that writes outside its data dir, from *any* author — not just the four here. Third-party poppies break silently and at the worst moment: an `existsSync` on a denied path throws instead of returning false, so "check then fall back" code crashes on the check, and denied reads inside vendored SDKs are often swallowed, so features go quiet instead of erroring. Worse, a poppy with no `dataDir` in its bootstrap does not degrade — the host **throws** at spawn (`backend-host.ts:151-152`).

**What has to be true first:**
1. Steps 2–9 done, so all first-party poppies are strict *explicitly* (before the default changes, so nothing depends on the default's timing).
2. A minimum host version gate. The validator only checks known keys and does not reject unknown ones (`manifest.ts:160-178`), so an older AgentsPoppy that predates `confinementOptions` silently runs a strict poppy **unconfined** rather than refusing. A `minHost` bump is what makes the flag mean anything.
3. Flip the default only for manifests submitted after a stated date, or require an explicit `"isolation": "none"` with a written reason at review, so an existing poppy is never confined by an update it did not ask for.
4. Developer docs and the poppy template updated first: write to `dataDir`, hand files out via `/local-download`, no child processes.

### (b) `backend.runtime` defaults to `"node22"` instead of `"native"`

Today: `const runtime = spec.manifest.backend.runtime ?? "native"` (`backend-host.ts:245`), and the SDK type says the same (`host-api.ts` / `manifest.ts:52-53` — "Defaults to `native`").

**What breaks when it flips:** any poppy that ships an executable and omits `runtime`. It would be run as a CJS bundle on the host's Node and fail immediately. That is a loud failure, not a silent one, which is the right direction — but it is still a break.

**What has to be true first:** an audit of every catalogued manifest for a backend with no `runtime` key. If any exist, add the explicit `"runtime": "native"` before flipping, or the flip breaks them. Note the runtime default is the *enabler* for the isolation default: strict requires node22 (`manifest.ts:176-177`), so a manifest that omits both would be rejected by the validator rather than confined. Flip runtime first, isolation second.

The related, arguably more valuable change is not a default at all: `SECURITY_MECHANISM.md:213-215` observes that a poppy shipping a backend at all is **not surfaced in the risk rating** — a user approving a connection sees a careful breakdown of AWS grants and no mention that native code is about to run on their machine. That is open task #50 and it matters more for this threat than any single grant.

## 5. What this does NOT fix

Be blunt about the limits, because the flag reads stronger than it is.

- **It is a runtime barrier, not an OS sandbox.** Node enforces it inside the process. It is not the kernel refusing. Anything that escapes the Node runtime escapes the allowlist. Real OS sandboxing (macOS App Sandbox / `sandbox-exec`, Windows AppContainer, Linux bubblewrap + seccomp) is stronger, needs a launcher per platform, and is not done (`SECURITY_MECHANISM.md:203-207`).
- **There is no network dimension.** The permission model denies filesystem paths, child processes, workers and native addons. It says nothing about sockets. A confined backend can still open any connection to anywhere and send whatever it holds in memory. Confinement stops a poppy *reading* `~/.aws/credentials`; it does not stop it exfiltrating what it legitimately obtained.
- **It cannot apply to a native binary at all.** The validator rejects `strict` on `runtime: "native"` (`manifest.ts:173-177`) precisely because there is no runtime of ours inside an opaque executable to enforce anything. So confinement covers node22 poppies only, and the honest answer for a native poppy is "unconfined", not "confined differently".
- **The temp directory is fully writable and shared.** `write = [dataDir, tmp]` (`backend-host.ts:154`). Two poppies can see each other's temp files. Temp is not a private space.
- **The install directory is readable, and the data dir is not private from the user or from other processes** running as the same OS user. Same OS user, same permissions — that is the whole point of the earlier note at `backend-host.ts:114-115`.
- **A denied read often looks like "no data", not like an error.** The AWS SDK swallows its shared-config read failures. MailPoppy's ledger returns `[]` on failure (`ledger.ts:32-40`); TrafficPoppy's backup listing returns `[]` (`backup.ts:144-149`). Confinement converts several real failures into quiet feature loss. That is the main reason each migration step above needs its own functional test rather than just "the poppy still boots".
- **It does not remove the need for the grant review.** A confined poppy still holds whatever AWS permissions its manifest was approved for.
- **Uninstall does not clean the data dir.** Moving state there is right, but nothing deletes it later (audit-observed). Files now accumulate somewhere the user does not browse.

## 6. How to verify a poppy is actually confined

"Declared confined" and "is confined" are different claims. Three checks, cheapest first. Run all three — the first two can both pass on a poppy that is not actually confined.

**Check 1 — the manifest that actually shipped (30 seconds).** Not the repo file. The release zip embeds its own `extension.json`, so unzip the published package (or read the installed copy under the host's extensions directory) and confirm `"backend": { "runtime": "node22", "isolation": "strict" }`. A repo-only edit ships nothing.

**Check 2 — the process really has the flags (2 minutes).** With the poppy running in the installed app, inspect the spawned backend's environment and confirm `NODE_OPTIONS` contains `--permission` plus `--allow-fs-read`/`--allow-fs-write` entries naming only the install root, the host data dir and the temp dir. On macOS: `ps -E` on the backend pid, or `ps eww <pid>`. If `NODE_OPTIONS` is absent, the poppy is running unconfined — most likely because the host predates `confinementOptions` and ignored the unknown key.

**Check 3 — the barrier actually bites (the one that proves it).** Add a temporary debug route to the poppy's backend that attempts a read the allowlist must refuse, and call it in the installed container:

```
// TEMPORARY — remove before release
app.get("/__confinement-check", async () => {
  const out: Record<string, string> = {};
  try { readFileSync(join(homedir(), ".aws", "credentials"), "utf8"); out.awsRead = "ALLOWED — NOT CONFINED"; }
  catch (e: any) { out.awsRead = e.code ?? String(e); }          // expect ERR_ACCESS_DENIED
  try { writeFileSync(join(homedir(), "Downloads", "x.tmp"), "x"); out.dlWrite = "ALLOWED — NOT CONFINED"; }
  catch (e: any) { out.dlWrite = e.code ?? String(e); }          // expect ERR_ACCESS_DENIED
  try { execSync("echo hi"); out.child = "ALLOWED — NOT CONFINED"; }
  catch (e: any) { out.child = e.code ?? String(e); }            // expect ERR_ACCESS_DENIED
  try { writeFileSync(join(dataDir, "x.tmp"), "x"); out.dataWrite = "ok"; }
  catch (e: any) { out.dataWrite = "BROKEN — " + (e.code ?? String(e)); }  // expect ok
  return out;
});
```

Pass = `ERR_ACCESS_DENIED` on the first three and `ok` on the fourth. The fourth matters as much as the others: it proves `dataDir` arrived and is writable, which is the thing MailPoppy's bootstrap parser currently drops (`agentspoppyBroker.ts:254-263`).

**Then the functional pass**, which is what actually catches the silent losses. For each poppy, exercise the feature that used to touch the disk and confirm it still produces a result rather than an empty list: MailPoppy — download an attachment, send one, download the bulk-import template, see ledger entries in the Resources tab, get the same buyer id twice. TrafficPoppy — back up, restart, **see the backup listed**, restore. VM-Poppy — launch a VM, fetch its key, decrypt a Windows password. CrewPoppy — export the crew CSV. A confined poppy that boots and answers `/health` has proven almost nothing.

# Appendix — host file-transfer affordances

## download

- **Exists:** true
- **Works confined:** true
- **How:** One dedicated host route; the poppy does most of the work. The BACKEND implements its own GET /local-download/:token HTTP route (the SDK ships no helper -- host-api.ts:195 only documents the convention). The FRONTEND builds the URL http://<brokerhost>/ext-dl/<extensionId>/local-download/<token> from its own window.location (it is served from the same broker origin at /ext-ui/<id>/...) and asks the host to open it in the system browser via openExternal. The broker route (http.ts:429-441) matches exactly 4 segments with parts[2]==="local-download", then calls registry.fetchBackendBytes(id, "/local-download/<token>") (registry.ts:306-319), which does a plain fetch("http://127.0.0.1:"+proc.port+path) and copies status, content-type and content-disposition back as raw bytes. The browser saves it because of Content-Disposition. WHO MINTS THE TOKEN: the poppy's own backend. The broker neither generates nor validates it -- the comment at http.ts:427-428 asserts tokens are single-use and short-lived, but nothing in http.ts or registry.ts checks that. MailPoppy is the reference: POST /local-download (mailpoppy node-sidecar/src/index.ts:146-165) takes {filename,contentType,dataB64} from the frontend, mints randomUUID(), and stores the decoded Buffer in an in-memory Map with a 60s TTL; GET /local-download/:token (index.ts:167-181) deletes the entry (single-use) and replies with the buffer plus content-disposition: attachment. The route is exempt from the broker auth gate (isAssetRoute, http.ts:123 and 126) so the OS browser, which carries no bearer token, can fetch it. openExternal is capability-gated (host-api.ts:86; capability host:openExternal at host-api.ts:117; gate at bridge.ts:113-114) and implemented at App.tsx:1061 via @tauri-apps/plugin-opener.
- **Evidence:** packages/broker/src/http.ts:423-441; packages/broker/src/http.ts:123,126 (auth exemption); packages/broker/src/extensions/registry.ts:298-319; packages/extension-sdk/src/host-api.ts:188-197; mailpoppy apps/desktop/node-sidecar/src/index.ts:142-181; mailpoppy apps/desktop/src/lib/localDownload.ts:19-28,50-64; agentspoppy app/src/App.tsx:1061; agentspoppy packages/broker/src/http.test.ts:299-350 (binary-safe passthrough + 404 for any other backend path)
- **Gaps:** The /ext-dl path itself needs ZERO filesystem access: fetchBackendBytes is an HTTP fetch (registry.ts:312) and MailPoppy's token store is an in-memory Map (index.ts:143). So it survives strict isolation intact. THREE real caveats. (1) MailPoppy's PREFERRED download path is NOT that route -- saveBytesToDownloads calls POST /local-download/save (index.ts:188-204), which does fsp.mkdir(join(homedir(),"Downloads")) + fsp.writeFile. So that route breaks. (3) There is no native save dialog anywhere: app/src-tauri/capabilities/default.json lists no dialog permission (only opener/notification/updater/process/deep-link), and app/src-tauri/Cargo.toml:18-29 has no tauri-plugin-dialog. - **Works confined:** true
- **How:** There is NO host-provided upload path at all -- no multipart route, no file picker, no SDK helper. Grepping 'type="file"|showOpenFilePicker|FileReader|dataTransfer|multipart' across app/src and packages/ (broker + extension-sdk) returns zero hits. The HostBridge surface (host-api.ts:70-107) has eleven methods and none of them is about files. Uploads work anyway, entirely on the FRONTEND side: the poppy's own page renders a normal <input type="file">, reads it with FileReader in the browser frame, and then either (a) POSTs the bytes straight to the network -- MailPoppy base64s the File in the frame (apps/desktop/src/lib/attachments.ts:6-29) and, for >=1MB, PUTs it directly to a presigned S3 URL (packages/api-client/src/index.ts:274-292), never touching the backend process -- or (b) hands it to its own backend as base64 inside a JSON body via HostBridge.invokeBackend (host-api.ts:84), which the host proxies: POST /extensions/:id/backend (http.ts:413-420) -> registry.proxyBackend (registry.ts:280-296) -> fetch to the backend's loopback port. The bytes therefore arrive at the backend as a JSON string, in memory.

- **Gaps:** Confinement is irrelevant to this direction and the code says why: confinementOptions returns a NODE_OPTIONS string that is applied only to the spawned backend child process (backend-host.ts:145-160, applied at backend-host.ts:288-296). The frontend is an iframe in the host's webview (ExtensionFrame.tsx:80-90) -- a browser context with no fs API to restrict. Reading a user-picked file there and POSTing it is unaffected. FOUR limits worth knowing. (1) JSON only: proxyBackend JSON.stringifies the body and res.text()s the reply (registry.ts:286-295), so binary must be base64 (~33% inflation) and there is no streaming or multipart. (2) No size cap: readJsonBody buffers the entire request into memory (http.ts:22-24) -- no limit is imposed, so a large upload is a memory cost, not a rejection. (3) If a confined backend wants the uploaded file ON DISK it may only write it under dataDir or the OS temp dir (backend-host.ts:154); anywhere else is ERR_ACCESS_DENIED. (4) UNVERIFIED: whether the OS file-picker actually opens for <input type="file"> inside the sandboxed iframe in the packaged Tauri webview (WKWebView/WebView2). No sandbox token governs file inputs and MailPoppy ships that input, but I found no test and no recorded live run of it inside the container -- only inside MailPoppy's own standalone Tauri shell. Worth a 10-minute manual check before relying on it.

## openExternal

A capability-gated HostBridge method. The frontend calls openExternal(url) on the client the SDK builds (bridge.ts:80), which postMessages a HostRequest to the host frame; ExtensionFrame.tsx:53-67 accepts it only if e.source is that frame's own contentWindow, then handleHostRequest checks that the manifest declared the required capability (bridge.ts:110-116, mapped host:openExternal at host-api.ts:117) before dispatching. The host implementation (App.tsx:1061-1071, wired in via createBrokerHostBridge, hostBridge.ts:49) dynamically imports @tauri-apps/plugin-opener and calls openUrl(url), falling back to window.open outside Tauri. The Rust side is permitted by "opener:default" in app/src-tauri/capabilities/default.json, scoped to windows:["main"]. Two things I checked and did NOT find: the host implementation performs no scheme/allowlist validation on the URL before handing it to the OS, and the frame is NOT granted Tauri IPC (the only capability file scopes to windows:["main"] and declares no remote URLs), so openExternal via the bridge is the poppy's only route to the OS browser. Confinement does not touch it -- it is entirely host-side.

## Verdict

Yes -- a confined poppy can do both, and the two directions do not work the same way. UPLOAD is untouched by confinement, because it never involves the confined process at all: the user picks a file with a plain <input type=\"file\"> in the poppy's sandboxed iframe (a browser context, ExtensionFrame.tsx:85), FileReader turns it into base64 in the frame, and it goes either straight to the network (MailPoppy: presigned S3 PUT, api-client/src/index.ts:274-292) or into the backend as a JSON body over invokeBackend (http.ts:413-420 -> registry.ts:280-296). NODE_OPTIONS confinement applies only to the spawned backend child (backend-host.ts:288-296), so nothing here is denied. The caveats are ergonomic, not permission-related: JSON/base64 only, no streaming, no size cap, and no host file picker or SDK helper exists -- every poppy rolls its own. DOWNLOAD is the direction that actually depends on the host, and the supported route survives cleanly: the backend mints its own token, holds the bytes in memory, and the OS browser fetches them through the unauthenticated /ext-dl/:id/local-download/:token passthrough (http.ts:429-441 -> registry.ts:306-319), which is pure HTTP -- no filesystem anywhere. So an email attachment can be downloaded and uploaded under strict isolation. THE WEAKER DIRECTION IS DOWNLOAD, and specifically MailPoppy's current default implementation of it: saveBytesToDownloads prefers POST /local-download/save, which writes into ~/Downloads (mailpoppy node-sidecar/src/index.ts:188-204). That is denied under strict (write allowlist is dataDir + tmp only, backend-host.ts:153-154; homedir access proven ERR_ACCESS_DENIED at backend-host.test.ts:182-183), and it fails LOUDLY rather than degrading, because the fallback to the browser handoff only fires on a 404 (localDownload.ts:96) while an access-denied arrives as a 500. Delete or re-gate that route before flipping MailPoppy to strict. One honest gap: I could not verify from code that the OS file picker opens for <input type=\"file\"> inside the sandboxed iframe in the packaged webview -- no sandbox token forbids it and MailPoppy ships the input, but there is no test or recorded in-container run. Check it manually before treating upload as proven.
